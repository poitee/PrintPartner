# Source snapshots

`pp-source` publishes a selected local file set as an immutable Source snapshot. The `pp-source` CLI uses the same `SourceRoot::materialize` API. The module owns filesystem bytes and the snapshot manifest. It does not own SQL, catalog activation, upload routes, or the desktop database lock. The media module composes bounded 3MF conversion with these immutable snapshots.

A trusted host opens `TenantRepos` from its configured absolute repository directory and authenticated tenant identity. After checking Source ownership in the catalog, it requests a `SourceRoot` for that Source ID. This constructor validates identity syntax and confines paths; it does not query or authenticate catalog ownership. Never expose these bootstrap constructors directly to HTTP, MCP, or untrusted command arguments. `LocalFiles` similarly represents a directory selected and authorized by the host.

`SnapshotRequest` carries the existing upstream revision key, validated `SourcePath` values, file kinds, and selection metadata. Materialization does not generate or replace revision identities. Existing valid revisions reuse their original content and selection even if the new request changes them. SQL revision IDs remain owned by the catalog.

`ArtifactBudget` bounds new content and manifest bytes for this operation. The caller must reserve and serialize tenant quota across Sources before calling. This module neither measures other tenant directories nor issues a quota reservation. The hard content ceiling is 1 GiB. STL count and non-STL bytes use the supplied selection limits. Additional bounds are 10,000 selected/omitted files, 10,000 filesystem entries including directories, 64 path components, 4,096 UTF-8 path bytes, and 8 MiB manifest/CLI JSON.

`SourcePath` on a new request is a relative, `/`-separated path in Unicode 17 NFC (the `unicode-normalization` pin must match the Unicode version of the pinned Node runtime). Node's `sourceRelativePath` applies the same structural and NFC rules for new paths. A version-1 manifest written when Rust used Unicode 16 NFC still loads: `a` + U+1ADD + U+0300 + `.stl` stays the stored filename and is not rewritten. That spelling is rejected for a new request. Unicode 16 also treated that spelling as distinct from `à` + U+1ADD + `.stl`, so a version-1 tree may contain both. Load compares those names with Unicode 16 NFC and reads each file by its exact stored name. New publication still rejects the legacy spelling and still treats Unicode 17 NFC collisions, including `café.stl` with `cafe` + U+0301, as duplicates. Rust additionally rejects:

- any `:`, so a path can never name a Windows drive (`C:x`) or an NTFS alternate data stream (`part.stl:stream`) when materialized on Windows. Node accepts colons, and existing Node snapshots or GitHub sources may contain them, so Node is intentionally not tightened;
- the manifest name `.printpartner-source-snapshot.json` as the first component of a longer path. Node rejects only the exact manifest path here and fails such a directory later at materialization;
- paths over the 4,096-byte and 64-component bounds below.

`rust/tests/source-artifacts/source-path-replay.mjs` reports these as documented Rust-only differences and fails on any other accept/reject or NFC difference.

Every directory component is opened with `O_NOFOLLOW` through a directory handle. Configured roots containing symlink aliases are rejected; trusted bootstrap may explicitly select the canonical directory. Each pinned component from `/` through the root is also checked with `fstat` on its handle: a component owned by anyone other than the effective user or root, or group/world-writable without the sticky bit, fails with `unsafe-ancestor`. The selected root itself must not be group/world-writable, even with the sticky bit: sticky ancestors are safe only when a subsequently checked component confines access below them. On macOS the extended ACL is also read from each pinned handle (`acl_get_fd_np`, never by path). An allow entry granting a write-class right (add file/subdirectory, delete, delete child, write attributes/extended attributes/security, change owner) to anyone other than the effective user or root fails with `unsafe-acl`; ACL read failures fail with `io`. This is stricter than the kernel: groups (even the user's own) and unresolvable UUIDs count as foreign, deny entries never offset a grant regardless of order, inheritable and inherit-only grants count, and sticky ancestors get no ACL exemption. Deny-only ACLs, such as those on `~/Documents`, are accepted. Files stream through a 64 KiB buffer. A per-Source advisory lock on the revisions directory serializes cooperating artifact writers, including live ZIP extraction readiness. It is not a database lock. The mutable Source handle also prevents simultaneous use of the same handle.

The single private `.pp-source-candidate` directory is disposable until publication. Under the directory lock, retry removes abandoned staging, validates any existing final snapshot, or stages again. Files, manifest, nested directories, and the candidate directory are synced before a non-overwriting rename. The revisions directory is synced after rename. An error after rename means the caller must retry the same revision key; retry verifies the final manifest and bytes. Published directories are never removed by staging cleanup. This is process-crash evidence on Linux, not proof of power-loss durability on every filesystem.

`PublishedSnapshot` is artifact readiness. It carries tenant and Source identity, unchanged upstream key, Node-compatible manifest digest, relative snapshot locator, content metadata, original selection, created/reused status, and stored bytes. The next catalog operation must independently validate ownership and perform its registration/activation transaction, including its observed-state check. A failed catalog transaction leaves a reusable artifact, not an activated Source.

The CLI accepts one JSON command on stdin and prints a receipt or error. It is an administrative consumer intended for host-authorized or disposable roots. See `rust/tests/source-artifacts/verify.py` for concrete commands and rerunnable Node parity checks. Literal percent filename route behavior remains unverified.


## ZIP extraction

`SourceRoot::extract_zip` takes `ZipInput`, `ArchiveLimits`, and an atomic cancellation flag. `ZipInput::open` accepts only an authorized `LocalFiles` capability and validated relative path. Extraction copies the input through a 64 KiB buffer into private staging, so later input-path replacement cannot redirect parsing. It preserves the original input and hashes the exact staged compressed bytes.

The private candidate is `<source>/revisions/.pp-source-archives/.candidate`. Extraction takes the same per-Source revisions lock as snapshot materialization and holds it for the entire lifetime of `ExtractedArchive`. The originating `SourceRoot` handle materializes under that held lock. The handle's materializations and its readiness share the flock through a holder count, so discarding readiness while that handle is still materializing (for example on another thread) keeps the lock until the last holder finishes. Any other handle, in this or another process, blocks in `materialize` until the readiness is discarded or dropped. A second extraction, or an extraction while another handle is materializing, returns `archive-busy` and preserves the live candidate. Each Source therefore stages at most one archive (compressed copy plus extracted files) and one snapshot candidate at a time, so tenant quota reservations for concurrent operations on one Source never stack staging copies. Do not materialize the same Source through a second handle on the thread that holds the readiness; that call waits for a lock its own thread holds. After process death, the operating system releases the lock and retry removes only this owned candidate. Neither extraction nor its cleanup deletes a revision.

`ExtractedArchive` is owned artifact readiness. Its `files()` capability can feed the existing snapshot API. Its receipt lists Source and tenant identity, compressed SHA-256, actual compressed/inflated byte counts, entry/STL counts, files and directories. Consume `discard()` to observe cleanup errors and release the Source lock promptly. Dropping an unused readiness value also attempts cleanup and releases the lock, but a destructor cannot report failure. Empty directories appear in the extraction receipt; the existing snapshot API preserves selected files and their parent directories only.

`pp-source-archive` is the concrete consumer. It reads an authorized JSON command, extracts, materializes the selected files using the supplied revision key, consumes extraction cleanup, and prints both receipts. It treats non-STL bytes as opaque artifacts. It does not expand 3MF, discover import rules, generate revisions, activate SQL, enforce tenant-global quota, or implement multipart HTTP uploads. The existing snapshot API retains first-valid-publication behavior for reused revision keys.

Default bounds are 256 MiB compressed, 1 GiB actual inflated bytes, and 10,000 archive entries. Callers may lower these limits. Each file entry may also inflate to at most 100 times its compressed size; entries up to 1 MiB inflated are exempt so small padding or empty files stay valid. The advertised central-directory size is checked before inflating, and violations return `compression-ratio`. Understated sizes cannot bypass the cap: the ZIP reader fails an entry once it inflates past its advertised size (`io: File is larger than its declared uncompressed size`), and the cap also bounds actual streamed bytes. A ZIP64 extra field replaces only the header sizes and offset that hold the 0xFFFFFFFF sentinel, in preflight and in the reader alike. Sizes the reader resolves must equal the checked central-directory sizes, or the archive is rejected as `invalid-archive: reader entry metadata differs from preflight`. Ordinary STL and document data compresses far below 100:1, while zero-filled bombs reach roughly 1000:1. Additional bounds are 8 MiB central-directory metadata, 10,000 distinct filesystem paths including implicit directories, and the existing Source path bounds. A bounded end record and central-directory pass runs before the ZIP crate allocates its index. The validated EOCD must be the only end record the reader may use: archive comments containing EOCD, ZIP64 EOCD, or ZIP64 locator signatures are rejected, and the staged copy is truncated to that EOCD with comment length cleared before `ZipArchive` opens. Because the ZIP crate falls back to earlier end records when the validated central directory fails its own parse, preflight walks every central extra field as the crate does: truncated record headers, records overrunning the field, empty or inconsistent extended timestamps, malformed NTFS fields, and ZIP64 fields too short for the values they replace return `invalid-archive: malformed extra field`; Unicode path/comment and AES fields return `unsupported-archive`. After opening, the reader's archive offset, central-directory start, comment, entry count, and each entry's central-header offset, local-header offset, name and sizes must equal what preflight recorded, or extraction fails with `invalid-archive: reader <field> differs from preflight`. Every produced chunk is checked before writing; advertised uncompressed lengths cannot bypass the actual-byte limit. The staged ZIP uses at most the compressed budget, extraction at most the inflated budget, and snapshot composition temporarily adds another content copy plus its manifest. The host must account for all these copies when reserving tenant quota.

Stored and Deflated single-disk archives are supported, including central-directory-resolved data descriptors. Entry paths must be NFC UTF-8 relative paths with forward slashes and no control characters. Absolute/backslash paths, duplicate/case-fold/prefix conflicts, symlinks, encryption flags, unsupported compression, multi-disk archives and malformed metadata are rejected. CRC is validated while reading. These are deliberate restrictions relative to Node's permissive duplicate overwrite, absolute-prefix stripping, symlink-payload conversion, and malformed-archive handling. See the actual Node/Rust corpus for the observed differences. macOS runtime is still unverified.

## Unicode collision policy

Archive inspection and snapshot validation share one path index. Each component's comparison key is Unicode 17 NFC, Unicode 16.0.0 full default case folding, then Unicode 17 NFC again. The exact `caseless =0.2.2` dependency supplies the C and F mappings from [Unicode CaseFolding-16.0.0.txt](https://www.unicode.org/Public/16.0.0/ucd/CaseFolding.txt). Its [iterator implementation](https://docs.rs/caseless/0.2.2/src/caseless/lib.rs.html) uses a static mapping table and two pending characters. `unicode-normalization =0.1.25` supplies Unicode 17 NFC. Folding can expand one scalar to at most three scalars. Path length, depth, and 10,000 indexed entry limits bound comparison storage, including omitted paths.

`Straße.stl` conflicts with `STRASSE.stl`; `Σ.stl`, `σ.stl`, and `ς.stl` conflict; `ﬃ.stl` conflicts with `FFI.stl`. Folding is locale independent and excludes Turkic mappings. `I` matches `i`, while `İ` matches `i` plus U+0307 and `ı` remains distinct. Parent aliases also conflict, so `Straße/a.stl` and `STRASSE/b.stl` reject even though the final filenames differ. Identically spelled shared directories remain valid.

This conservative application rule is deliberately stricter than actual Node, which accepted the sharp-s pair in the frozen review. It makes no claim that APFS treats that pair as equivalent. Non-NFC input remains invalid. A composed/decomposed pair therefore rejects without renaming the decomposed entry. Comparison keys never replace stored filenames or feed manifest digests. Accepted Unicode spelling, UTF-16 lexical ordering, bytes, revision identities, and unambiguous snapshot reuse stay unchanged.

Previously accepted snapshots with ambiguous names now fail validation and reuse. Reuse first verifies the manifest digest, tree, and content hashes. If the revision is intact and the earlier whole-path `to_lowercase` rule accepted its names, it fails with the distinct `ambiguous-revision` error, which names the revision key. Corrupted revisions still report `corrupt-snapshot`, and names the earlier rule also rejected still report `duplicate-path`. `ambiguous-revision` is permanent, not transient: hosts must not retry it or treat it as a busy/IO failure. The module does not rename, rewrite, delete, or repair those immutable revisions. The migration path is operator-driven: publish the corrected file set under a new upstream revision key, activate it in the catalog, and then deactivate the old revision. The old directory remains on disk for audit until an operator removes it.

Omitted documentation paths keep Node parity. They dedupe among themselves with Rust `str::to_lowercase` and conflict with selected paths only on exact spelling. Only selected paths use full Unicode case folding. `Straße.stl` selected with `STRASSE.stl` omitted is therefore accepted.

## ZIP64 metadata

The bounded inspector resolves local ZIP64 size fields, central ZIP64 size and offset fields, the ZIP64 end record, and its locator. A ZIP64 disk sentinel may resolve to disk zero. Multiple disks remain unsupported. Forced-small ZIP64, signed and unsigned data descriptors, Stored entries, and Deflated entries stay within the same compressed, inflated, entry, metadata, and path limits. Physical entries must cover the data region without gaps or overlaps. Their names, flags, sizes, CRC metadata, and optional descriptors must agree with central records.

Actual Node has a known Stored-entry defect with an unsigned descriptor. It reports success but drops the final four payload bytes. Rust retains the full CRC-verified payload. `rust/tests/source-media/verify-zip64.py` asserts this exact divergence separately from the byte-parity cases. Existing CRC, encryption, collision, symlink, and malformed-metadata restrictions remain deliberate safety differences.

## Media preparation

`SourceRoot::prepare_media` accepts authorized `LocalFiles`, selected original paths, selected directory paths, `MediaLimits`, and a cancellation flag. Its owned `PreparedMedia` holds an exclusive lock on `<source>/revisions/.pp-source-media` and a private `.candidate` directory. A concurrent owner receives `media-busy`. Retry removes only an abandoned candidate. `discard()` reports cleanup failures. Drop attempts cleanup when an owner exits without publication.

The candidate retains exact original files, including ZIP and 3MF artifacts. Each selected 3MF outside an exact `_3mf` path component expands into `_3mf/<project>/<object>.stl`. Original or derived path collisions refuse the whole operation. A failed conversion publishes no derived files. The host passes `PreparedMedia::files()` and its selected-file receipt to the existing `materialize` operation for one immutable publication. Previously accepted revisions retain their original bytes and selection.

Model preflight reads only the bounded ZIP index, local metadata, and the first physical `.model` member. It validates the declared model size before retaining model bytes and checks actual bytes before extending the buffer. Accepted originals are then copied into the private candidate. Conversion reads the staged original again, so derived bytes correspond to the retained package. This preserves confinement when input pathnames change. `modelRead` reports conversion reads and seeks, excluding preflight, original copy, and snapshot copy. The successful original copy necessarily reads the complete selected package.

`ModelDocument` owns bounded document text. The parser follows the current Node regex grammar instead of claiming full XML validation. It preserves Node's case-insensitive unprefixed element matching, attribute and entity handling, default IDs and names, part-number omission, unit scales, duplicate slug numbering, and case-sensitive `.3mf` basename removal. Some malformed XML and mesh text inside XML comments therefore remain accepted, as in Node. Namespace-prefixed objects do not gain new semantics. Only direct meshes convert. Components and build transforms are ignored, and component-only documents refuse.

The parser stores one `MeshObject` at a time and checks counts before each vertex or triangle push. Hard defaults are 64 MiB raw model bytes, 2,000 mesh objects, 5,000,000 vertices, 10,000,000 triangles, 256 MiB total derived bytes, and 1 GiB combined original and derived bytes. Callers may lower these positive limits. Count limits apply per model document. Derived and total byte limits apply to the complete preparation. Serialized derived-file receipt metadata has a separate 8 MiB aggregate ceiling, enforced through a counting writer before retaining each receipt. This prevents highly compressed object names across packages from accumulating large receipt buffers. Node has no equivalent aggregate receipt guard. The existing 10,000 indexed-path ceiling also applies.

Slug normalization retains the pinned Unicode 16 collision dependency and adds the Unicode 17 ASCII compatibility mapping for U+A7F1, MODIFIER LETTER CAPITAL S, only during slugging. An actual Node oracle checks every Unicode scalar alone and between ASCII letters. Collision keys keep their existing Unicode 16 policy.

ASCII STL bytes use exact `ryu-js =1.0.2` ECMAScript number formatting. Normals follow the operation order of [Node 24.21.0's three-argument Math.hypot](https://raw.githubusercontent.com/nodejs/node/v24.21.0/deps/v8/src/builtins/math.tq). A finite cross product whose length overflows preserves Node's finite zero normal. Geometry that would emit Infinity or NaN refuses. XML character references to surrogate code points also refuse because Rust strings contain Unicode scalar values. These are explicit safety differences. Existing originals and accepted artifacts survive refusal.

`discover_import_rules` returns top-level directories first, then top-level STL and 3MF filenames. It keeps a sole wrapper directory and ignores opaque ZIP files as import rules. Within each group, names use the native Node scan ordering observed on Linux. The distinguishing supplementary-plane and private-use BMP fixture is retained. Snapshot digest ordering remains UTF-16. Empty directories supplied by archive extraction contribute discovery rules but are not files in the snapshot manifest.

`pp-source-media` is the concrete administrative CLI. A command provides tenant and Source identity, authorized absolute roots, a revision key, and either `files` or `zipPath`. Optional `limits` and `archiveLimits` lower the hard limits. ZIP mode composes extraction, media preparation, snapshot publication, and consuming cleanup. Its stdout contains extraction metadata when applicable, Node-compatible conversion receipts, selected original and derived files, import rules, read counters, and the published snapshot receipt.

The host must reserve all temporary copies: compressed ZIP staging, inflated extraction, original media copies, derived media files, and snapshot composition plus its manifest. This module does not reserve tenant-global quota or perform SQL registration, activation, authorization, multipart handling, scanner/catalog integration, route cutover, or macOS runtime verification. A failed catalog transaction must retain accepted immutable bytes for retry.

The rerunnable differential tools are `rust/tests/source-media/verify.py`, `verify-zip64.py`, `edge-probe.py`, `failure-probe.py`, and `measure.py`. They invoke the public Rust CLI and existing built Node authorities. No Node runtime is part of the Rust implementation.
