# Source snapshots

`pp-source` publishes a selected local file set as an immutable Source snapshot. The `pp-source` CLI uses the same `SourceRoot::materialize` API. The module owns filesystem bytes and the snapshot manifest. It does not own SQL, catalog activation, upload routes, 3MF conversion, or the desktop database lock.

A trusted host opens `TenantRepos` from its configured absolute repository directory and authenticated tenant identity. After checking Source ownership in the catalog, it requests a `SourceRoot` for that Source ID. This constructor validates identity syntax and confines paths; it does not query or authenticate catalog ownership. Never expose these bootstrap constructors directly to HTTP, MCP, or untrusted command arguments. `LocalFiles` similarly represents a directory selected and authorized by the host.

`SnapshotRequest` carries the existing upstream revision key, validated `SourcePath` values, file kinds, and selection metadata. Materialization does not generate or replace revision identities. Existing valid revisions reuse their original content and selection even if the new request changes them. SQL revision IDs remain owned by the catalog.

`ArtifactBudget` bounds new content and manifest bytes for this operation. The caller must reserve and serialize tenant quota across Sources before calling. This module neither measures other tenant directories nor issues a quota reservation. The hard content ceiling is 1 GiB. STL count and non-STL bytes use the supplied selection limits. Additional bounds are 10,000 selected/omitted files, 10,000 filesystem entries including directories, 64 path components, 4,096 UTF-8 path bytes, and 8 MiB manifest/CLI JSON.

Every directory component is opened with `O_NOFOLLOW` through a directory handle. Configured roots containing symlink aliases are rejected; trusted bootstrap may explicitly select the canonical directory. Files stream through a 64 KiB buffer. A per-Source advisory lock on the revisions directory serializes cooperating artifact writers. It is not a database lock. The mutable Source handle also prevents simultaneous use of the same handle.

The single private `.pp-source-candidate` directory is disposable until publication. Under the directory lock, retry removes abandoned staging, validates any existing final snapshot, or stages again. Files, manifest, nested directories, and the candidate directory are synced before a non-overwriting rename. The revisions directory is synced after rename. An error after rename means the caller must retry the same revision key; retry verifies the final manifest and bytes. Published directories are never removed by staging cleanup. This is process-crash evidence on Linux, not proof of power-loss durability on every filesystem.

`PublishedSnapshot` is artifact readiness. It carries tenant and Source identity, unchanged upstream key, Node-compatible manifest digest, relative snapshot locator, content metadata, original selection, created/reused status, and stored bytes. The next catalog operation must independently validate ownership and perform its registration/activation transaction, including its observed-state check. A failed catalog transaction leaves a reusable artifact, not an activated Source.

The CLI accepts one JSON command on stdin and prints a receipt or error. It is an administrative consumer intended for host-authorized or disposable roots. See `rust/tests/source-artifacts/verify.py` for concrete commands and rerunnable Node parity checks. Literal percent filename route behavior remains unverified.


## ZIP extraction

`SourceRoot::extract_zip` takes `ZipInput`, `ArchiveLimits`, and an atomic cancellation flag. `ZipInput::open` accepts only an authorized `LocalFiles` capability and validated relative path. Extraction copies the input through a 64 KiB buffer into private staging, so later input-path replacement cannot redirect parsing. It preserves the original input and hashes the exact staged compressed bytes.

The private candidate is `<source>/revisions/.pp-source-archives/.candidate`. An advisory lock on the archive parent is held for the entire lifetime of `ExtractedArchive`. A second extraction for that Source returns `archive-busy`, preserving the live candidate. After process death, the operating system releases the lock and retry removes only this owned candidate. Neither extraction nor its cleanup deletes a revision.

`ExtractedArchive` is owned artifact readiness. Its `files()` capability can feed the existing snapshot API. Its receipt lists Source and tenant identity, compressed SHA-256, actual compressed/inflated byte counts, entry/STL counts, files and directories. Consume `discard()` to observe cleanup errors. Dropping an unused readiness value also attempts cleanup, but a destructor cannot report failure. Empty directories appear in the extraction receipt; the existing snapshot API preserves selected files and their parent directories only.

`pp-source-archive` is the concrete consumer. It reads an authorized JSON command, extracts, materializes the selected files using the supplied revision key, consumes extraction cleanup, and prints both receipts. It treats non-STL bytes as opaque artifacts. It does not expand 3MF, discover import rules, generate revisions, activate SQL, enforce tenant-global quota, or implement multipart HTTP uploads. The existing snapshot API retains first-valid-publication behavior for reused revision keys.

Default bounds are 256 MiB compressed, 1 GiB actual inflated bytes, and 10,000 archive entries. Callers may lower these limits. Additional bounds are 8 MiB central-directory metadata, 10,000 distinct filesystem paths including implicit directories, and the existing Source path bounds. A bounded end record and central-directory pass runs before the ZIP crate allocates its index. Every produced chunk is checked before writing; advertised uncompressed lengths cannot bypass the actual-byte limit. The staged ZIP uses at most the compressed budget, extraction at most the inflated budget, and snapshot composition temporarily adds another content copy plus its manifest. The host must account for all these copies when reserving tenant quota.

Stored and Deflated single-disk archives are supported, including central-directory-resolved data descriptors. Entry paths must be NFC UTF-8 relative paths with forward slashes and no control characters. Absolute/backslash paths, duplicate/case-fold/prefix conflicts, symlinks, encryption flags, unsupported compression, multi-disk/ZIP64 end records, and malformed metadata are rejected. CRC is validated while reading. These are deliberate restrictions relative to Node's permissive duplicate overwrite, absolute-prefix stripping, symlink-payload conversion, and malformed-archive handling. See the actual Node/Rust corpus for the observed differences. macOS runtime is still unverified.

## Unicode collision policy

Archive inspection and snapshot validation share one path index. Each component's comparison key is NFC, Unicode 16.0.0 full default case folding, then NFC again. The exact `caseless =0.2.2` dependency supplies the C and F mappings from [Unicode CaseFolding-16.0.0.txt](https://www.unicode.org/Public/16.0.0/ucd/CaseFolding.txt). Its [iterator implementation](https://docs.rs/caseless/0.2.2/src/caseless/lib.rs.html) uses a static mapping table and two pending characters. Existing `unicode-normalization =0.1.24` supplies NFC. Folding can expand one scalar to at most three scalars. Path length, depth, and 10,000 indexed entry limits bound comparison storage, including omitted paths.

`Straße.stl` conflicts with `STRASSE.stl`; `Σ.stl`, `σ.stl`, and `ς.stl` conflict; `ﬃ.stl` conflicts with `FFI.stl`. Folding is locale independent and excludes Turkic mappings. `I` matches `i`, while `İ` matches `i` plus U+0307 and `ı` remains distinct. Parent aliases also conflict, so `Straße/a.stl` and `STRASSE/b.stl` reject even though the final filenames differ. Identically spelled shared directories remain valid.

This conservative application rule is deliberately stricter than actual Node, which accepted the sharp-s pair in the frozen review. It makes no claim that APFS treats that pair as equivalent. Non-NFC input remains invalid. A composed/decomposed pair therefore rejects without renaming the decomposed entry. Comparison keys never replace stored filenames or feed manifest digests. Accepted Unicode spelling, UTF-16 lexical ordering, bytes, revision identities, and unambiguous snapshot reuse stay unchanged.

Previously accepted snapshots with ambiguous names now fail validation and reuse. The module does not rename, rewrite, delete, or repair those immutable revisions. Callers must handle that compatibility error; retry cannot silently replace an accepted revision.

ZIP64 compatibility remains incomplete. The reviewed seekable `force_zip64=True` small archive is accepted by actual Node and rejected here because its local size markers differ from ordinary central sizes. A forced-small ZIP64 descriptor archive was accepted through central metadata resolution. ZIP64 end records remain rejected. Neither observation establishes general ZIP64 support. This Unicode correction changes no inflation or ZIP parsing behavior.
