# OAuth authorization-start parity

`node.json` records the real Fastify `registerAuthRoutes` handlers for eight cases. Both GitHub and Discord run enabled and disabled with loopback HTTP and secure-cookie configurations. Every case runs twice. The generator reuses the existing parity generators' tsx child process and the storage fixtures' `SqliteDatabase` setup with a real `AuthStore` in a disposable directory.

The Rust consumer drives the public `auth_router` over a loopback listener with a disposable `WriterOwner`. Credentials are fake. The configured callback origins are fixed loopback addresses so callback URI drift remains visible without port normalization. The listeners bind ephemeral ports. Rust requests supply the configured Host. Secure rows exercise HTTPS callback configuration and the Secure cookie attribute through a local HTTP test connection. They do not test TLS or browser cookie delivery. Node drives Fastify injection after opening its loopback listener.

Redirects remain HTTPS URLs for the public provider authorization endpoints. Neither client follows redirects. The suite never requests a provider, exchanges tokens, signs in, or calls a callback. GRE-867 owns callback consumption and refusal coverage.

Each row retains the exact status, redirect origin and path, complete decoded query multimap, complete cookie attribute map, and response body. Values for repeated query keys retain their order. Unknown keys, duplicate values, omitted values, changed callback URIs, changed cookie attributes, and disabled-provider redirects fail the comparison.

Node state must be fresh lowercase hexadecimal with 16 bytes. Before replacing it with `<state>`, the generator asserts that exactly one redirect state equals the only `oauth_state` cookie. It checks this binding on both requests. Raw generated values never enter the golden or success logs. Rust response comparisons suppress response payloads in assertion failures.

The consumer records two intentional security corrections. It does not claim byte equality for those fields.

- Rust issues independent 32-byte base64url state and browser binding values. The test checks their canonical encoding, inequality, and freshness before using `<state>` and `<browser-binding>`. Equality fails before normalization.
- GitHub additionally sends `code_challenge` and `code_challenge_method=S256`. The challenge must be canonical unpadded base64url for 32 bytes and fresh across starts. Only its generated bytes become `<pkce-s256>`. Both PKCE keys remain in the exact expected multimap. Discord must have neither key. The private verifier is unavailable through the public start response, so this slice cannot prove the challenge's SHA-256 relation to that verifier. GRE-867 owns callback flow behavior.

Both implementations emit `Max-Age=600`, `Path=/`, `HttpOnly`, and `SameSite=Lax`. Fastify supplies the default SameSite attribute even though the handler omits that option. Secure rows additionally require `Secure`. Node GitHub omits `response_type`. Discord requires `response_type=code`. The comparison preserves those differences between providers.

Disabled-provider bodies currently differ. The fixture pins Node GitHub's `GitHub OAuth not configured. Set GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET, GITHUB_CALLBACK_URL.` and Node Discord's `Discord OAuth not configured`. The Rust consumer separately pins `OAuth not configured` for both providers. This is an explicit existing message difference, not a security correction or a claim of identical responses. Both sides must return exactly 501 without a Location or Set-Cookie header. Changing either literal fails. No production change is included.

Run from the repository root with Node 22 and the web dependencies installed.

```sh
node fixtures/parity/auth-authorization-start/generate.mjs
node fixtures/parity/auth-authorization-start/generate.mjs --check
PP_SCHEMA_PARITY_NODE=/path/to/node22 cargo test --manifest-path rust/Cargo.toml \
  -p pp-api --features desktop_rebuild --test auth_authorization_start_parity
```

The Rust tests are entirely behind default-off `desktop_rebuild`. The freshness test invokes Node 22 and `--check`. An explicit `PP_SCHEMA_PARITY_NODE` is authoritative. An invalid explicit executable fails without fallback. Without that variable, the test invokes `node` from PATH and still requires version 22. This slice changes no runtime routing, environment gates, or user behavior.
