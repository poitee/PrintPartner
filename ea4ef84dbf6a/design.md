# GRE-353 explicit account mapping

The latest GRE-353 receipt leaves validated native actions, explicit owner mapping and Mac release acceptance open. The main audit selected owner mapping because Node currently refuses every existing-account database. Linux can prove the account and tenant through the real gateway and supervised Node child.

Two independent design runners read the architecture. Codex compared Node translation with core forwarding. Grok compared an explicit signed account pin with a narrowly allowlisted external handoff. Both selected account mapping as the next useful work. The parent selected Node translation because Node already owns compatibility account lookup and session metadata. Rust retains its fixed signed transport identity. The Node mapping applies only after that signature and request binding pass.

The data shape is Synthetic or Existing with an explicit pinned account mapping. The supported mapping names the account and its same-id tenant. Legacy default-tenant ownership and data migrations remain open. The runtime preserves the selected account's actual admin status and refreshes account metadata per authenticated request. No header, cookie or request body chooses a tenant.

Both the Cargo desktop_rebuild feature and captured PP_DESKTOP_REBUILD setting must enable the trusted child setup discriminator. With either off, setup omits it and existing-account refusal remains. No native permissions change.

Admission reads a bounded private regular mapping file without following symlinks. It validates a current existing database read-only before product startup. The startup probe showed that ordinary SQLite connect restores default starter profiles and repairs foreign source-revision ownership. The mapped path must skip that maintenance, limit background tenants to the named tenant and refuse backup replacement.

The throughput checkpoint has four parts. Mapping admission and startup mutation audit block implementation proof. Independent workstreams do not apply because the setup and authentication changes share one contract. One implementation owner writes the bound branch while fixtures use isolated directories. One owner is the smallest safe decomposition for this change.

Acceptance requires actual gateway bootstrap, selected-account metadata, own-tenant reads and writes, foreign-ID denial, persisted tenant values, restart, malformed and unsafe map refusal before product writes, unchanged foreign and default records, and both flag gates. Compilation and a delegate report are insufficient. Exact-head proof, settled CI and a fresh Grok Build score above 8 gate merge.

No Mac, signed-release, validated handoff or full GRE-353 completion claim is made.
